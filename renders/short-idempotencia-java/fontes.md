# Fontes do Short "Idempotência em Java" (produção de 2026-11-07)

Conferência feita em 2026-11-07 por leitura direta das páginas (texto em inglês citado literalmente).

## Fontes fichadas

1. **RFC 9110, HTTP Semantics, seção 9.2.2 "Idempotent Methods"**
   https://www.rfc-editor.org/rfc/rfc9110.html
   - Definição: "A request method is considered "idempotent" if the intended effect on the server of multiple identical requests"
   - Lista: "Of the request methods defined by this specification, PUT, DELETE, and safe request methods are idempotent."
   - Uso no Short: o método POST de um pagamento não é idempotente pela definição da RFC. Por isso a chave.

2. **IETF Internet-Draft `draft-ietf-httpapi-idempotency-key-header-08`** (Active Internet-Draft, httpapi WG; não é RFC)
   https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/
   - Resumo: "The HTTP Idempotency-Key request header field can be used to make non-idempotent HTTP methods such as POST or PATCH"
   - Seção 2: "An idempotency key is a unique value generated by the client which the resource uses to recognize subsequent retries"
   - Seção 2.6: "The resource SHOULD respond with a response consistent with the request being completed according to the user's intent."
   - Uso no Short: a ideia de chave única por pagamento e de repetição reconhecida pela chave. O rascunho não diz
     que o servidor devolve o primeiro resultado: esse é o desenho da demonstração, não citação.
