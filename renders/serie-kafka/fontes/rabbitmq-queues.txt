[P4] ## What is a Queue?​

[P5] A queue in RabbitMQ is an ordered collection of messages. Messages are enqueued and dequeued (delivered to consumers) in a (FIFO ("first in, first out") manner.

[P6] To define a queue in generic terms, it is a sequential data structure with two primary operations: an item can be enqueued (added) at the tail and dequeued (consumed) from the head.

[P7] Queues play a major role in the messaging technology space. Many messaging protocols and tools assume that publishers and consumers communicate using a queue-like storage mechanism.

[P8] Many features in a messaging system are related to queues. Some RabbitMQ queue features such as priorities and requeueing by consumers can affect the ordering as observed by consumers.

[P9] The information in this topic includes an overview of queues in RabbitMQ and also links out to other topics so you can learn more about using queues in RabbitMQ.

[P10] info

[P11] In addition to queues, modern RabbitMQ versions support two alternative data structures called streams and super streams.

[P12] This guide primarily covers queues in the context of the AMQP 0-9-1 protocol, however, much of the content is applicable to other supported protocols.

[P13] Some protocols (for example: STOMP and MQTT) are based around the idea of topics. For these protocols, queues act as a data accumulation buffer for consumers. However, it is still important to understand the role queues play because many features still operate at the queue level, even for those protocols.

[P14] Streams is an alternative messaging data structure available in RabbitMQ. Streams provide different features from queues.

[P30] ## Queue Names​

[P31] Queues have names so that applications can reference them.

[P32] Applications may pick queue names or ask the broker to generate a name for them. Queue names may be up to 255 bytes of UTF-8 characters.

[P33] Queue names starting with "amq." are reserved for internal use by the broker. Attempts to declare a queue with a name that violates this rule will result in a channel-level exception with reply code 403 (ACCESS_REFUSED).

[P34] ## Server-named Queues​

[P35] In AMQP 0-9-1, the broker can generate a unique queue name on behalf of an app. To use this feature, pass an empty string as the queue name argument: the same generated name may be obtained by subsequent methods in the same channel by using the empty string where a queue name is expected. This works because the channel remembers the last server-generated queue name.

[P36] Server-named queues are meant to be used for state that is transient in nature and specific to a particular consumer (application instance). Applications can share such names in message metadata to let other applications respond to them (as demonstrated in tutorial six). Otherwise, the names of server-named queues should be known and used only by the declaring application instance. The instance should also set up appropriate bindings (routing) for the queue, so that publishers can use well-known exchanges instead of the server-generated queue name directly.

[P37] ## Queue Properties​

[P38] Queues have properties that define how they behave. There is a set of mandatory properties and a map of optional ones:

[P39] Name

[P40] Durable (the queue will survive a broker restart)

[P41] Exclusive (used by only one connection and the queue will be deleted when that connection closes)

[P42] Auto-delete (queue that has had at least one consumer is deleted when last consumer unsubscribes)

[P43] Arguments (optional; used by plugins and broker-specific features such as message TTL, queue length limit, etc)

[P44] important

[P45] Note that not all property combination make sense. For example, exclusive queues should almost always be server-named.

[P46] Such queues are supposed to be used for client-specific or connection (session)-specific data.

[P47] When exclusive queues use well-known (static) names, in case of client disconnection and immediate reconnection there will be a natural race condition between RabbitMQ nodes that will delete such queues and recovering clients that will try to re-declare them. This can result in client-side connection recovery failure or exceptions, and create unnecessary confusion or affect application availability.

[P48] ## Declaration and Property Equivalence​

[P49] tip

[P50] Specifically for the queue type property, the property equivalence check can be relaxed. Alternatively, a default queue type (DQT) can be configured.

[P51] Before a queue can be used it has to be declared. Declaring a queue will cause it to be created if it does not already exist. The declaration will have no effect if the queue does already exist and its attributes are the same as those in the declaration. When the existing queue attributes are not the same as those in the declaration a channel-level exception with code 406 (PRECONDITION_FAILED) will be raised.

[P52] Specifically for the queue type property, the property equivalence checks can be relaxed or configured to use a default.

[P53] See the Virtual Hosts guide to learn more.

[P54] ## Optional Arguments​

[P55] Optional queue arguments, also known as "x-arguments" because of their field name in the AMQP 0-9-1 protocol, is a map (dictionary) of arbitrary key/value pairs that can be provided by clients when a queue is declared.

[P56] The map is used by various features and plugins such as

[P57] Queue type (e.g. quorum or classic)

[P58] Message and queue TTL

[P59] Queue length limit

[P60] Quorum queue redelivery limit

[P61] Max number of priorities of a classic queue

[P62] and so on.

[P63] The same idea is also used with other protocol operations, for example, when registering a consumer:

[P64] Consumer priorities

[P65] Some optional arguments are set at queue declaration time and remain immutable over the entire lifetime of the queue. Others can be dynamically changed after queue declaration via policies.

[P66] For keys that can be set via policies, always first consider using a policy instead of setting these values in application code

[P67] For example, queue type (x-queue-type) and max number of queue priorities (x-max-priority) must be set at queue declaration time and cannot be changed after that.

[P68] Optional queue arguments can be set differently:

[P69] To groups of queues using policies (recommended)

[P70] On a per-queue basis when a queue is declared by a client

[P71] For the x-queue-type argument, using a default queue type

[P72] The former option is more flexible, non-intrusive, does not require application modifications and redeployments. Therefore it is highly recommended for most users. Note that some optional arguments such as queue type or max number of priorities can only be provided by clients because they cannot be dynamically changed and must be known at declaration time.

[P73] The way optional arguments are provided by clients varies from client library to client library but is usually an argument next to the durable, auto_delete and other arguments of the function (method) that declares queues.

[P74] ## Optional Arguments and Policy-Defined Key Precedence​

[P75] When the same key is provided by both client-provided x-arguments and by a policy, the former take precedence.

[P76] However, if an operator policy is also used, that will take precedence over the client-provided arguments, too. Operator policies are a protection mechanism and override client-provided values and user policy values.

[P77] For numerical values such as maximum queue length or TTL, the lower value of the two will be used. If an application needs or chooses to use a lower value, that will be allowed by an operator policy. A value higher than that defined in the operator policy, however, cannot be used.

[P78] Use operator policies to introduce guardrails for application-controlled parameters related to resource use (e.g. peak disk space usage).

[P79] ## Message ordering​

[P80] Message ordering matters when there are causal dependencies between messages. RabbitMQ tries to preserve the order of messages.

[P81] A queue is an ordered collection of messages providing FIFO semantics. When publishing on a single channel, messages are enqueued in publishing order in every queue they are routed to. When publishing happens on multiple connections or channels, their sequences of messages will be routed concurrently and interleaved. Delivery from a queue to consumers proceeds in enqueue order (unless below events occur).

[P82] ## When messages can be reordered​

[P83] Even if RabbitMQ aims to preserve order, the following will change effective delivery order:

[P84] Message priorities: higher-priority messages may be delivered before lower-priority messages.

[P85] Multiple active consumers on the same queue: the broker still dequeues in FIFO, but any redelivery can change order. Redelivery happens when consumers negatively acknowledge with requeue or a channel/session closes with unacked messages. Redelivered messages are flagged (AMQP 1.0: first-acquirer=false, AMQP 0-9-1: redelivered=true).

[P86] ## Preserving message order​

[P87] To preserve message order in RabbitMQ you have two options.

[P88] ### 1.) Use a stream​

[P89] A stream is an immutable append-only log. Each message gets its offset assigned at publish-time. This offset never changes.

[P90] Multiple consumers can process messages from the same stream concurrently without affecting ordering. With stream filtering, you can split work so that different consumers process disjoint subsets of the stream while preserving order within each subset.

[P91] ### 2.) Use a queue with a single active consumer​

[P92] To keep order with queues:

[P93] Enable Single Active Consumer so only one consumer receives messages at a time. (Alternatively, run one consumer per queue.)

[P94] If your consumers return messages to the queue, make sure they return those messages in the order they received them.

[P95] For quorum queues, set a delivery limit. This ensures messages are requeued at the front of the queue.

[P96] AMQP 0-9-1: don’t use basic.get. When stopping a consumer, prefer closing the channel over basic.cancel.

[P97] If you need to process messages concurrently while preserving order for each domain entity (e.g. per order ID), you can use the x-modulus-hash exchange to partition messages across multiple queues, each with a single active consumer.

[P98] ## Durability​

[P99] Queues can be durable or transient (non-durable). Metadata of a durable queue is stored on disk, while metadata of a transient queue is stored in memory when possible. The same distinction is made for messages at publishing time in some protocols, e.g. AMQP 0-9-1 and MQTT.

[P100] In environments and use cases where durability is important, applications must use durable queues and make sure that publishers mark published messages as persisted.

[P101] Durable queues will be recovered on node boot, including messages in them published as persistent. Messages published as transient will be discarded during recovery, even if they were stored in durable queues.

[P102] Transient queues will be deleted on node boot. They therefore will not survive a node restart, by design. Messages in transient queues will also be discarded.

[P103] warning

[P104] Transient (non-durable) non-exclusive classic queues are deprecated and cannot be declared by default starting with RabbitMQ 4.3.0.

[P105] Please use one of the following:

[P106] durable queues

[P107] non-durable exclusive queues

[P108] durable queues with a queue TTL (a reasonably close equivalent to non-exclusive transient queues)

[P109] To explicitly allow transient non-exclusive queues, add the following line to rabbitmq.conf:

[P110] # Enables deprecated non-durable (transient) non-exclusive queues

[P111] # (disabled by default as of RabbitMQ `4.3.0`, will be removed in a later version)

[P112] deprecated_features.permit.transient_nonexcl_queues = true

[P113] ## How to Choose​

[P114] In most other cases, durable queues are the recommended option. For replicated queues, the only reasonable option is to use durable queues.

[P115] Throughput and latency of a queue is not affected by whether a queue is durable or not in most cases. Only environments with very high queue or binding churn — that is, where queues are deleted and re-declared hundreds or more times a second — will see latency improvements for some operations, namely on bindings. The choice between durable and transient queues therefore comes down to the semantics of the use case.

[P116] Temporary queues can be a reasonable choice for workloads with transient clients, for example, temporary WebSocket connections in user interfaces, mobile applications and devices that are expected to go offline or use switch identities. Such clients usually have inherently transient state that should be replaced when the client reconnects.

[P117] Some queue types do not support transient queues. Quorum queues must be durable due to the assumptions and requirements of the underlying replication protocol, for example.

[P118] ## Temporary Queues​

[P119] With some workloads queues are supposed to be short lived. While clients can delete the queues they declare before disconnection, this is not always convenient. On top of that, client connections can fail, potentially leaving unused resources (queues) behind.

[P120] RabbitMQ supports a number of queue properties that make sense for the data that is transient or client-specific in nature. Some of these settings can be applied to durable queues but not every combination makes sense.

[P121] Consider using server-generated names for exclusive temporary queues. Since such queues are not meant to be shared between N consumers, using unique names makes sense.

[P122] There are three ways to make queue deleted automatically:

[P123] Exclusive queues (covered below)

[P124] TTLs (also covered below)

[P125] Auto-delete queues

[P126] An auto-delete queue will be deleted when its last consumer is cancelled (e.g. using the basic.cancel in AMQP 0-9-1) or gone (closed channel or connection, or lost TCP connection with the server).

[P127] If a queue never had any consumers, for instance, when all consumption happens using polling, it won't be automatically deleted. For such cases, use exclusive queues or queue TTL.

[P128] Queue TTL can be used for cleanup of unused durable queues.

[P129] When RabbitMQ detects a non-durable and non-exclusive queue, it will display a deprecation warning in the management UI.

[P130] ## Exclusive (Client Connection-Specific) Queues​

[P131] An exclusive queue can only be used (consumed from, purged, deleted, etc) by its declaring connection. Such queues are by definition temporary in nature, setting the exclusive property on a durable queue does not make logical sense since such queue cannot outlive its declaring connection, and thus cannot satisfy its durability property in case of a node restart.

[P132] Queues declared as exclusive will always be declared as classic queues: exclusive quorum queues and streams do not make logical sense as their lifetimes would be bound to the lifetime of a specific client connection and thus a single node (or application instance).

[P133] Consider using server-generated names for exclusive queues. Since such queues cannot be shared between N consumers, using server-generated names makes most sense.

[P134] An attempt to use an exclusive queue from a different connection will result in a channel-level exception RESOURCE_LOCKED with an error message that says cannot obtain exclusive access to locked queue.

[P135] Exclusive queues are deleted when their declaring connection is closed or gone (e.g. due to underlying TCP connection loss). They therefore are only suitable for client-specific transient state.

[P136] It is common to make exclusive queues server-named.

[P137] Exclusive queues are declared on the "client-local" node (the node that the client declaring the queue is connected to), regardless of the queue_leader_locator value.

[P138] ## Replicated and Distributed Queues​

[P139] Quorum queues is replicated, data safety and consistency-oriented queue type. Classic queues historically supported replication but this feature was removed for RabbitMQ 4.x.

[P140] Any client connection can use any queue, whether it is replicated or not, regardless of the node the queue replica is hosted on or the node the client is connected to. RabbitMQ will route the operations to the appropriate node transparently for clients.

[P141] For example, in a cluster with nodes A, B and C, a client connected to node A can consume from a queue Q hosted on B, while a client connected to node C can publish in a way that routes messages to queue Q.

[P142] Client libraries or applications may choose to connect to the node that hosts the current leader replica of a specific queue for improved data locality.

[P143] This general rule applies to all messaging data types supported by RabbitMQ except for one. Streams are an exception to this rule, and require clients, regardless of the protocol they use, to connect to a node that hosts a replica (a leader of rollower) of the target stream. Consequently, RabbitMQ Stream protocol clients will connect to multiple nodes in parallel.

[P144] Queues can also be federated across loosely coupled nodes or clusters.

[P145] Note that intra-cluster replication and federation are orthogonal features and should not be considered direct alternatives.

[P146] Streams is another replicated data structure supported by RabbitMQ, with a different set of supported operations and features.

[P147] ## Non-Replicated Queues and Client Operations​

[P148] Any client connection can use any queue, including non-replicated (single replica) queues, regardless of the node the queue replica is hosted on or the node the client is connected to. RabbitMQ will route the operations to the appropriate node transparently for clients.

[P149] ## Time-to-Live and Length Limit​

[P150] Queues can have their length limited. Queues and messages can have a TTL.

[P151] Both features can be used for data expiration and as a way of limiting how many resources (RAM, disk space) a queue can use at most, e.g. when consumers go offline or their throughput falls behind publishers.

[P152] ## In Durable and In-Memory Storage​

[P153] In modern RabbitMQ versions, quorum queues and classic queues v2 alike actively move data to disk and only keep a relatively small working set in memory.

[P154] In some protocols (e.g. AMQP 0-9-1) clients can publish messages as persistent or transient. Transient messages will still be stored on disk but will be discarded during the next node restart.

[P155] In AMQP 0-9-1, this is done via a message property (delivery_mode or, in some clients, persistent).

[P156] Other relevant guides on the topic are Quorum Queues, Streams, Reasoning About Memory Usage, Alarms, Memory Alarms, Free Disk Space Alarms, Deployment Guidelines, and Message Store Configuration.

[P157] ## Priorities​

[P158] Queues can have 0 or more priorities. This feature is opt-in: only queues that have maximum number of priorities configured via an optional argument (see above) will do prioritisation.

[P159] Publishers specify message priority using the priority field in message properties.

[P160] If priority queues are desired, we recommend using between 1 and 10. Currently using more priorities will consume more resources (Erlang processes).

[P161] ## CPU Utilisation and Parallelism Considerations​

[P162] Currently a single queue replica (whether leader or follower) is limited to a single CPU core on its hot code path. This design therefore assumes that most systems use multiple queues in practice.

[P163] danger

[P164] A single queue is generally considered to be an anti-pattern, and not just for resource utilisation reasons.

[P165] For workloads that push queue throughput to the limits, consider using streams or partitioned streams with a RabbitMQ Stream Protocol client.

[P166] ## Metrics and Monitoring​

[P167] RabbitMQ collects multiple metrics about queues. Most of them are available via RabbitMQ HTTP API and management UI, which is designed for monitoring. This includes queue length, ingress and egress rates, number of consumers, number of messages in various states (e.g. ready for delivery or unacknowledged), number of messages in RAM vs. on disk, and so on.

[P168] rabbitmqctl can list queues and some basic metrics.

[P169] Runtime metrics such as VM scheduler usage, queue (Erlang) process GC activity, amount of RAM used by the queue process, queue process mailbox length can be accessed using the rabbitmq-top plugin and individual queue pages in the management UI.

[P170] ## Consumers and Acknowledgements​

[P171] Messages can be consumed by registering a consumer (subscription), which means RabbitMQ will push messages to the client, or fetched individually for protocols that support this (e.g. the basic.get AMQP 0-9-1 method), similarly to HTTP GET.

[P172] Delivered messages can be acknowledged by consumer explicitly or automatically as soon as a delivery is written to connection socket.

[P173] Automatic acknowledgement mode generally will provide higher throughput rate and uses less network bandwidth. However, it offers the least number of guarantees when it comes to failures. As a rule of thumb, consider using manual acknowledgement mode first.

[P174] ## Prefetch and Consumer Overload​

[P175] Automatic acknowledgement mode can also overwhelm consumers which cannot process messages as quickly as they are delivered. This can result in permanently growing memory usage and/or OS swapping for the consumer process.

[P176] Manual acknowledgement mode provides a way to set a limit on the number of outstanding (unconfirmed) deliveries: channel QoS (prefetch).

[P177] Consumers using higher (several thousands or more) prefetch levels can experience the same overload problem as consumers using automatic acknowledgements.

[P178] High number of unacknowledged messages will lead to higher memory usage by the broker.

[P179] ## Message States​

[P180] Enqueued messages therefore can be in one of two states:

[P181] Ready for delivery

[P182] Delivered but not yet acknowledged by consumer

[P183] Message breakdown by state can be found in the management UI.

[P184] ## Determining Queue Length​

[P185] It is possible to determine queue length in a number of ways:

[P186] With AMQP 0-9-1, using a property on the queue.declare method response (queue.declare-ok). The field name is message_count. How it is accessed varies from client library to client library.

[P187] Using RabbitMQ HTTP API.

[P188] Using the rabbitmqctl list_queues command.

[P189] Queue length is defined as the number of messages ready for delivery.

[P190] ## Avoid Temporary Queues with Well-Known Names​

[P191] A temporary queue that is not exclusive can be client named and shared between multiple consumers. This, however, is not recommended and can lead to a race condition between RabbitMQ node operations and client recovery.

[P192] Consider the following scenario:

[P193] A consumer uses an auto-delete queue with a well-known names

[P194] Client's connection fails

[P195] Client detects it and initiates connection recovery

[P196] As the failed connection which had the only consumer on an auto-delete queue, the queue must be deleted by RabbitMQ. This operation will take some time, during which the consumer may recover.

[P197] Then depending on the timing of operations, the queue can be

[P198] Declared by the recovering client and then deleted

[P199] Deleted and then re-declared

[P200] In the first case, the client will try to re-register its consumer on a queue that's been concurrently deleted, which will lead to a channel exception.

[P201] There are two solutions to this fundamental race condition:

[P202] Introduce a connection recovery delay. For example, several RabbitMQ client libraries use a connection recovery delay of 5 seconds by default

[P203] Use server-named queues, which side steps the problem entirely since the new client connection will use a different queue name from its predecessor
